## Context

Cobrix (a fictional name) processes B2B debt collection on behalf of other companies. Each debt carries a history of events — settlement, dispute, partial payment, suspension — and the collection deadline extends or not depending on how those events interact.

## Constraints

- The computed deadline needs an auditable explanation, not just a result.
- Recalculating the entire base cannot lock the database or block production queries during processing.
- New business rules, per contract type, need to be addable without changing the already-tested core.

## Architecture

The calculation core is a library with no dependency on Spring, JPA, or any HTTP client — it takes events, applies precedence and interval consolidation, and returns a result with the reasoning behind each decision. Around it, adapters (REST API, batch job, persistence layer) translate between the outside world and that core. A strategy registry picks the correct rule implementation per contract type.

## What did not work

The first version processed each event in arrival order, layering the most recent on top of the previous one. It worked until two competing events — an open dispute and a signed settlement in the same window — produced different deadlines depending on data import order: a silent, hard-to-reproduce bug. The fix was to stop relying on arrival order and model precedence explicitly.

## Main lesson

In a rule engine, the right question is not "which event won," but "can I prove why it won, a year from now, in an audit?"
