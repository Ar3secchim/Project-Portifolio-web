## Context

This service came from a simple question: how do I show that the homelab exists and works without giving any visitor a path, direct or indirect, into the real cluster.

## Constraints

- No new inbound port could be opened on the cluster to support this use case.
- Whatever got published had to stay safe even if the schema changed or a new field was forgotten.
- Testing the service could not depend on running against the homelab’s own production cluster.

## Architecture

A Go CronJob runs periodically inside the cluster, collects counts and GitOps sync status, assembles a versioned JSON document, and validates it against a closed schema before publishing to a bucket. A pattern scanner (hostnames, secrets) runs as a last gate before upload. A local dev server with fully fictional data lets the service be iterated on without ever touching the real cluster.

## What did not work

An early idea was reading node and workload counts directly from a broader Kubernetes API — simpler to implement, but it required a wider RBAC permission than necessary. The trade was inferring those numbers from more restricted signals, accepting more code in exchange for a smaller permission scope.

## Main lesson

Security by design here meant something concrete: the service cannot leak what it was never granted permission to read.
