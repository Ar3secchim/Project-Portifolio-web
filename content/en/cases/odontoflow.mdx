## Context

OdontoFlow started as an attempt to design a real B2B SaaS from scratch: multiple clients (clinics), multiple users per client, recurring billing, and sensitive patient data — all running on serverless infrastructure.

## Constraints

- Two organizations can never see each other’s data, even if a new endpoint has an implementation mistake.
- Recurring billing has to survive payment-provider event delivery failures without duplicating or missing a charge.
- Staging and production environments must come from the same infrastructure definition, not diverging manual steps.

## Architecture

Each serverless function passes through a middleware layer — authentication, schema validation, error handling — before reaching a controller, which delegates to a service. Services apply business rules and always receive an already-resolved organization context. Payment, storage, and email gateways isolate external integrations behind internal interfaces.

WhatsApp appointment reminders follow the same principle: each clinic has its own messaging instance, so one organization’s number and session never serve another. Infrastructure comes from Terraform modules (Cognito, S3, SES, and a budget alert) instantiated for development, staging, and production.

## Two decisions recorded as ADRs

**ADR-003 — A fully private bucket, served by a Worker that signs requests.** The frontend used to be served from a public S3 bucket: anyone could fetch files directly, bypassing Cloudflare. The options were keeping the bucket public or paying for an AWS CDN. The choice was a Cloudflare Worker that signs each request with AWS SigV4 and also handles the SPA route fallback — no public access to the bucket, zero CDN cost.

**ADR-009 — Payments behind an interface, not an SDK.** Calling the Stripe SDK straight from services would have been faster, but it would spread the provider across the whole application. The decision was a gateway interface with one adapter per provider; switching providers changes a single construction point. In the webhook, each event has a unique ID and is only recorded as processed after it is handled successfully — a provider redelivery never duplicates a charge.

## What did not work

The first subscription model treated the payment provider as the source of truth and queried its API on every access check — slow and fragile against external instability. The fix was keeping an internal subscription state, updated by event, using the external provider only as a trigger.

## Main lesson

Multi-tenancy is not an organization column on a table. It is a rule that must be present — and tested — on every path that touches sensitive data.
