## Contexto

Este serviço nasceu de uma pergunta simples: como mostrar que o homelab existe e funciona sem dar a qualquer visitante um caminho, direto ou indireto, até o cluster real.

## Restrições

- Nenhuma porta de entrada nova podia ser aberta no cluster para atender este caso de uso.
- O que fosse publicado precisava ser seguro mesmo se o schema mudasse ou um campo novo fosse esquecido.
- Testar o serviço não podia depender de rodar contra o cluster de produção do próprio homelab.

## Arquitetura

Um CronJob em Go roda periodicamente dentro do cluster, coleta contagens e status de sincronização do GitOps, monta um documento JSON versionado e o valida contra um schema fechado antes de publicar em um bucket. Um scanner de padrões (nomes de host, segredos) roda como última barreira antes do upload. Um servidor de desenvolvimento local, com dados totalmente fictícios, permite iterar no serviço sem tocar no cluster real.

## O que não funcionou

Uma primeira ideia era ler diretamente contagens de nós e workloads via uma API mais ampla do Kubernetes — mais simples de implementar, mas exigia uma permissão RBAC maior do que o necessário. A troca foi inferir esses números a partir de sinais mais restritos, aceitando mais código em troca de um escopo de permissão menor.

## Aprendizado principal

Segurança por design, aqui, significou uma coisa concreta: o serviço não consegue vazar o que nunca teve permissão para ler.
